# Markdown 表格优化方案

## 0. 结论摘要

| 优先级 | 项目 | 目标 | 改动面 | 风险 |
| --- | --- | --- | --- | --- |
| P0（已实施，见 §8） | 按格增量测量 | 同格打字不再逐格重建 span 树与 `TextPainter` | `table_measure.dart` + `table_block.dart` | 中 |
| P1-A（已实施，见 §9） | 超宽表格改为换行 | 不再用负 `letterSpacing` 硬挤，宽表可读 | 列宽策略 + 行高 | 中高 |
| P2（已实施，见 §10） | 零散 `TextPainter` 缓存 | 行内代码基线、抓手图标、`_middleOverhang` | 局部小改 | 低 |
| P2（已实施，见 §11） | 表头开关 | 右键菜单可「设为表头 / 取消表头」 | `TableCommands` + 菜单 | 低 |

推荐路径：先做 P0（含回归与性能护栏），再做 P1 的方向决策，最后收尾 P2。
本轮只出方案，不改代码。

## 1. 现状与证据

### 1.1 渲染与测量链路

表格不是 Flutter `Table`，而是引擎级自绘：

1. `LiveTableBlocks.blockFor`（`lib/ui/editor/live_markdown/table_block.dart:67-86`）在「整篇文本 / 正文样式 / 内容宽度 / 字号 / 方向 / 光标」任一变化时调用 `_measure`；
2. `_measure`（同文件 `:97-250`）按表格源码块配对旧记录：源码块相同且光标仍在同一格才整表复用，否则 `dispose` 全部行块并重跑 `_measureTable`（`:163-189`）；
3. `_measureTable`（`table_measure.dart:258-480`）三趟：
   - 第一趟（`:309-346`）每格 `_inline` 建 span 树 + `_measureSpans` 建 `TextPainter` 量自然宽；编辑中的格子额外再建一棵树、再测一次；
   - 第二趟（`:371-390`）分配列宽，总宽超过正文宽时先按 `_kMinCell` 地板比例挤压，地板也放不下则整体线性缩小；
   - 第三趟（`:394-430`）把挤压量烘焙成负 `letterSpacing`（`_squeeze`，`:170-203`）；
4. `_TableLineBlock._measureCells`（`table_block.dart:432-448`）为**每格再建一个 `TextPainter`**（`maxLines: 1`, `ellipsis: '…'`），`_chipsFor`（`:451-494`）又为每段行内代码新建一个 painter 量基线。

### 1.2 已具备的能力（本次不再重复建设）

对齐语法、`\|` 与 `<br>` 转义、TSV 复制/粘贴、行列增删/移动/复制/转置/排序/聚合、Ctrl+D/Ctrl+R 填充、F2 多行单元格编辑、Tab 导航、拖拽抓手与 `+`、按格子矩形的选区色带、跨表缓存（P1 已完成）。

### 1.3 问题证据

- **同格输入仍重测整表**：`_sourceKeyOf`（`table_block.dart:254-255`）是整张表源码拼接，键入一个字符即 key 变化 → 整表重测。`test/live_markdown_reuse_perf_test.dart:257-270` 断言 3 次输入带来 3 次整表测量；该测试只验证了「只重测所在表」，没有验证「表内只重测该格」。
- **每格成本是双份的**：`_measureTable` 第一趟每格 1 次 `layout`，`_measureCells` 每格再 1 次；100 × 10 的表每次按键约 2000 次 `layout`。方案文档 §5.1 已实测：去掉表格后编辑路径从 ~160ms 降到 ~95ms，表格是编辑时最大的固定成本。
- **宽表可读性**：10 列较宽内容放进 680px 时，列宽会被压到约 52px，负字距约 -4px/字符，字符相互重叠。
- **测试缺口**：`test/table_measure_cache_test.dart` 的 6 个用例没有「同一格内连续输入」。

### 1.4 本轮不做

- 不改 Markdown 源文件格式与命令语义；
- 不做列宽拖拽（必须把宽度写进源码，不可接受）；
- 不重写按行排版引擎，也不改 P2 的差分脏行机制。

## 2. P0：按格增量测量

### 2.1 核心思路

现状的缓存粒度是「整张表」，而一次按键真正变的只有**一个格子**。把粒度下沉到格子：

- 格的 **span 树 + 自然宽** 只与「格子显示文本 + 是否表头」有关（在同一个 `LiveTableBlocks` 实例内，调色板、正文样式、字号、方向、宽度都是常量）；
- 格的 **`TextPainter` + 行内代码底片** 只与「那棵 span 树 + 列宽」有关；
- 于是同格打字时，整表仍然重测（保持现有记录语义），但每格的昂贵工作全部命中缓存。

### 2.2 为什么可以缓存到「文本 + 是否表头」

对非编辑格，`_measureTable` 用的是 `plain` 上下文（`table_block.dart:132-142`）：`caretA/caretB = -1`、`selA/selB = -1`、`hoverA = -1`、`plain = true`。因此：

- `ctx.touched` / `ctx.selected` / `ctx.hovered` 恒为 false，行内代码与标签的 span 只由 `AppPalette` 决定；
- `_CellCode.start/end` 是**格内相对偏移**（`m.start/m.end`），与格子的绝对 `from` 无关；
- 唯一随环境变化的是 `contentWidth`（仅 `_imageSpan` 使用），而宽度变化本来就会触发整表重测与缓存清空。

所以键可以只是 `(cell.text, header)`。

### 2.3 数据结构

在 `LiveTableBlocks` 内新增（与 `_records`、`_bandCache` 同级）：

```dart
class _CellMemo {
  final String text;          // tableCellDisplay 之后的显示文本
  final bool header;
  final List<InlineSpan> rendered;  // 未挤压的树，painter 与命中都读它
  final List<_CellCode> codes;      // 行内代码/标签区间
  final double natural;             // 未挤压自然宽
  // 最近一次挤压结果：ls 未变就直接复用
  double squeezedFor = double.nan;
  List<InlineSpan> squeezed = const <InlineSpan>[];
}

class _CellMemoStore {
  final Map<(String, bool), _CellMemo> cells = {};
  final Map<(Object, int), _PaintedCell> painted = {}; // 键: memo 身份 + 列宽(1/4px 量化)
  int generation = 0;
  void beginMeasure() => generation++;
  void sweep();   // 清掉本轮没有用到的条目并 dispose 其中的 painter
  void clear();   // 环境变化 / dispose
}

class _PaintedCell {
  final TextPainter painter;   // maxWidth = 列宽文本区
  final List<_PaintedChip> chips;
  int usedIn = 0;
}
```

`_PaintedCell` 的唯一所有者是 store；`_TableLineBlock` 只持有引用，`dispose()` 不再销毁 painter（现有「重复 dispose 不抛异常」用例保持）。

### 2.4 改动点

**`table_measure.dart`**

- `_measureTable` 增加参数 `_CellMemoStore memo`。
- 第一趟（`:309-346`）：
  - 非编辑格：先查 `memo.cells[(text, header)]`，命中直接用 `rendered / codes / natural`，不再 `_inline`、不再 `_measureSpans`；未命中才建并写回；
  - 编辑格：保持现状（建 rendered 树用于列宽 + revealed 树用于绘制），**不写入 memo**（每击键文本都变）。
- 第三趟（`:394-430`）：
  - `ls == 0` 或 `ls == memo.squeezedFor` → 复用 `memo.squeezed`；
  - 否则 `_squeeze` 后写回 `squeezedFor / squeezed`。
- 第二趟列宽分配逻辑完全不变（仍是整表一起分配，保证列宽一致）。

**`table_block.dart`**

- `_TableLineBlock` 构造时不再 `new TextPainter`，改为向 store 取 `_PaintedCell`：
  - 键 = `(memo, quantize(cell.width))`；
  - 命中：`_painters.add(painted.painter)`、`_chips.add(painted.chips)`；
  - 未命中：按现有 `_measureCells` / `_chipsFor` 逻辑建一次并登记。
- `_measure` 开头 `memo.beginMeasure()`，结束 `memo.sweep()`；环境变化与 `_disposeBlocks` 时 `memo.clear()`。
- 新增测试计数：`@visibleForTesting int debugCellSpanBuilds`、`int debugCellPainterBuilds`。

### 2.5 失效矩阵

| 触发 | 表记录 | 格 memo | painter |
| --- | --- | --- | --- |
| 表格外编辑 / 正文光标移动 | 复用 | 保留 | 保留 |
| 表格上方插删行 | 复用 + `_rebind` | 保留 | 保留 |
| 同一格内打字 | 重测整表（现状不变） | **仅该格重建** | **仅该格 + 列宽变化列** |
| 光标跨格 | 该表重测（现状） | 进出两格重建 | 进出两格重建 |
| 内容宽度 / 字号 / 方向变化 | 全部重测 | 清空 | 清空 |
| 主题 / 正文样式变化 | 新实例（`_resolveTableBlocks` 已按样式缓存） | 新实例 | 新实例 |
| 选区变化 | 不重测（色带缓存） | 保留 | 保留 |

### 2.6 预期收益

- 常见（未挤压）表格，同格打字的格内成本从 `O(行 × 列)` 降到 `O(1) + 编辑列的 行数`：
  - span 树构建：1000 → 1；
  - 自然宽 `layout`：1000 → 2（rendered + revealed）；
  - 格 painter `layout`：1000 → 1 ~ 行数（编辑列列宽变化时最多每行 1 个）。
- 挤压型宽表仍会因列宽重分配而重建较多 painter，但第一趟的 O(格数) 成本同样被去掉。
- 表级对象（`_CellData`、`_TableLineBlock`）仍每击键重建，属轻量分配，不在本方案范围。

### 2.7 风险与护栏

1. **列宽依赖**：painter 的 `maxWidth = cell.width`，所以键里必须带列宽；列宽一变就得重建，不能想当然复用。
2. **挤压一致性**：`_squeeze` 是跳过首字符的负字距，`squeezedFor` 必须精确匹配 `ls`（用 `==` 比较 double，由同一条公式产出，安全）。
3. **所有权**：painter 与 chips 只由 store dispose；`_TableLineBlock.dispose` 只清引用。加 `assert` 防止 store 清空后仍被绘制。
4. **sweep 的生命周期**：sweep 必须在一次 `_measure` 所有表处理完之后执行，否则先处理的表会误删后处理表的条目。
5. **编辑格不写 memo**：避免把 revealed 树当成普通渲染树缓存。
6. **浮点列宽**：painter 键量化到 1/4px，避免亚像素抖动造成无谓 miss。

### 2.8 测试清单

在 `test/table_measure_cache_test.dart` 增补（沿用现有「走生产入口 `blockFor`」的写法）：

1. 同一格连续输入 3 次：`debugTableMeasures +3`；编辑格从不入 memo，`debugCellSpanBuilds +0`；列宽不变时 `debugCellPainterBuilds +3`，列宽被撑宽时 `+3 × 该列行数`。
2. 未编辑格的 painter 命中：连续输入后 `debugCellPainterBuilds` 不随其他格增加。
3. 增量结果与「全新 `LiveTableBlocks`」逐偏移等价：`offsetAt` 每格每偏移、`caretRectAt` 每偏移、`chromeCells()` 矩形一致。
4. 内容宽度或字号变化：`memo` 清空，一次重测的 `debugCellSpanBuilds` 等于格数。
5. 删除行 / 删除表后 sweep 生效：`debugCellPainterBuilds` 不再增长，重复 `dispose` 安全。
6. 性能（`@Tags(['perf'])`，单独运行）：`live_markdown_reuse_perf_test.dart` 增「100 × 10 表内同格打字」场景，记录数值并设宽松上限；与现状对比应显著下降。

### 2.9 退出条件

- `flutter analyze lib test` 无问题；
- `flutter test --exclude-tags perf` 全量通过（现有 856 项 + 新增）；
- perf 测试单独运行通过，100 × 10 冷布局不回退（62.7ms 基线，±10%）；
- 记录「100 × 10 表内同格打字」改造前后数值，下降不少于 70%。

## 3. P1：超宽表格可读性（需先定方向）

> 已选定 **A（单元格换行）** 并落地，实施细节与实测见 §9。

### 3.1 三个候选

| 方案 | 做法 | 效果 | 改动面 | 风险 |
| --- | --- | --- | --- | --- |
| A. 单元格换行 | 取消负字距；列宽给可读地板，格子按列宽换行，行高随内容增长 | 宽表完全可读，表格变高 | 列宽策略 + `_measureCells` + 行高 | 中高 |
| B. 横向滚动 | 保持单行自然宽，表格在正文区内横向滚动 | 保持紧凑，不换行 | 每表滚动状态 + 绘制裁剪/平移 + 命中换算 + 滚动条 | 高 |
| C. 收窄内边距 | 密集表把 `_kCellPad` 8 → 4，并设挤压可读下限 | 10 列多出约 80px；仍会挤压 | 极小 | 低 |

### 3.2 推荐 A，理由

- 现有架构已经天然支持「逐行不同高度」：`_TableLineBlock._contentHeight` 取 `max(表默认行高, 各格 painter 高度)`（`table_block.dart:432-448`），`_textTop`、色带、抓手、命中都以它为准；`_Table.dyShift` 与 `TableGeometry.rowHeight` 目前在 lib 内**没有消费方**（只有构造）。
- 取消负字距后，`_measureCells` 的 painter 宽度就是列宽，`offsetAt / caretRectAt / highlightRects` 的多行行为由 `TextPainter` 原生支持。
- B 需要在自绘行之间共享滚动偏移，还要与文本拖选手势、抓手、`+` 命中协调，复杂度明显更高。
- C 只是缓解，不能消除重叠。

### 3.3 若选 A：具体改法

1. `_measureTable` 第二趟改为「可读优先」：
   - 自然总宽 + 内边距 ≤ 可用宽 → 列宽 = `max(natural, _kMinCell)`（保持现状，单行）；
   - 否则给每列一个可读地板（建议 `_kReadableCol = 88`，随字号缩放），按自然宽比例分配剩余空间，**不再产生负 `letterSpacing`**；
   - 极端列数（`cols × 地板 > 可用宽`）才退回等分，允许长词按字符断行。
2. 删除第三趟的 `_squeeze / _spaced` 挤压流程与 `_CellData.letterSpacing`（或保留字段恒为 0，供过渡期断言）。
3. `_TableLineBlock._measureCells` 去掉 `maxLines: 1` 与 `ellipsis`，`layout(maxWidth: cell.width)`，`_contentHeight` 取各格 `tp.height` 最大值。
4. 逐个复核几何：`_textTop`（每格垂直居中）、`caretRectAt`（`getFullHeightForCaret` 已是行高）、`highlightRects`（多行 boxes）、色带（整块行高）、抓手（`_contentHeight` 居中）、F2 浮动编辑器锚点（用 `chromeCells()` 的矩形，自动变高）。
5. P2 的差分脏行无需改动：一张表重测时其全部行块已被替换，表行的连带失效已存在。

### 3.4 若选 A：验收

- 10 列宽内容表格：列宽不低于可读地板，`letterSpacing` 恒为 0，字符不重叠；
- 行高逐行不同，滚动范围与 `chromeCells()` 同步；
- 每个偏移的 `offsetAt → caretRectAt → offsetAt` 往返一致（沿用 `live_markdown_structure_test.dart` 的「光标扫过每个字符」护栏）；
- 视觉回归：普通窄表与现状像素级一致（不换行时高度与列宽不变）。

### 3.5 待决策

- 是否接受「宽表变高」；
- 可读地板取 88px 还是按字号（如 6em）计算；
- 是否保留 `<br>` 的 `↵` 显示（换行后仍可保留，因为它是显式换行）。

## 5. P2：表头开关（独立小功能，已实施）

> 已实现，见 §11。

- 模型已支持：`TableGrid.header`（`lib/core/utils/table_model.dart:352`）、无分隔行的表格能被 `TableBlock.parse` 识别（`:268-312`），`render` 会按 `header` 决定是否写分隔行（`:390`）。
- 新增 `TableCommands.setHeader(TableBlock block, bool header)`：
  - `true`：在第一行后插入分隔行，沿用当前列数与对齐（默认 `---`）；
  - `false`：删除分隔行；若对齐信息存在则一并丢弃（现有 `setAlign` 已约定「没有分隔行就没有对齐」）。
- 菜单：加在「数据」子菜单或「行」子菜单，标签「设为表头 / 取消表头」，用 `table.hasHeader` 决定 checked。
- 测试：有表头 → 取消 → 再设回，表格行列数不变、光标仍在原格、对齐按约定处理。

## 8. P0 实施记录

已按 §2 落地：`_CellMemoStore`（`table_measure.dart`）按 `(格文本, 是否表头)` 缓存 span 树 / code runs / 自然宽，按 `(memo, 列宽量化 1/4px)` 缓存 `TextPainter` 与 chips；`LiveTableBlocks` 每代 `beginMeasure → touch → sweep`，编辑格不入缓存、painter 归行块私有（`_owned`），共享 painter 由 store 统一释放。`_CellData.memo` 为新增字段。

实测（本机，`flutter test --tags perf`）：

| 场景 | 改造前 | 改造后 |
| --- | --- | --- |
| 100 × 10 表内同格打字 | 41.88 ms/次 | 6.08 ~ 8.53 ms/次（−80% ~ −85%） |
| 100 × 10 冷布局（`live_markdown_perf_test`） | 55.09 ms/build | 57.97 ms/build（+5.2%，在退出条件的 ±10% 内） |

测试：`table_measure_cache_test.dart` 8 项全过（新增「同一格连续输入只重建该格」「增量测量与全新实例的几何一致」）；`live_markdown_reuse_perf_test.dart` 新增 100 × 10 场景，断言每击键 `debugCellSpanBuilds` 不增、`debugCellPainterBuilds +1`、耗时 `< 30 ms`。全量 `flutter test --exclude-tags perf` 858 项通过，`flutter analyze lib test` 无问题。

注意：按格 painter 的键包含列宽，所以「被编辑的格撑宽了所在列」时该列每一格都会重排——这是测量正确性的约束，不是缓存漏命中；本次 perf 夹具因此让首列表头宽于数据格，以测出纯增量路径。挤压型宽表仍会因列宽重分配而重建较多 painter（见 §2.6）。

## 9. P1 实施记录（方案 A：单元格换行）

已按 §3.3 落地。列宽策略在 `table_measure.dart` 第二趟：

- 自然宽总和 + 内边距 ≤ 可用宽（窄表）：列宽 = `max(natural, _kMinCell)`，**与改造前完全一致**（单行，行高仍为基准行高）；
- 放不下时：每列先取 `min(自然宽, 可读地板)`，可读地板为 `_kReadableCol = 88` 按字号/无障碍缩放折算（`table_model.dart`）；剩余空间按各列「还想要的宽度」等比分配；
- 极端情况 `cols × 地板 > 可用宽`：全部等分，长词允许在格内折断。

其余改动：

1. 删除 `_squeeze / _spaced / _restyle` 三个挤压辅助函数与 `_CellMemo.squeezed / squeezedFor`、`_CellData.letterSpacing / advance / natural`；`_CellData.textX` 固定为 `x + _kCellPad`，对齐交给 painter 自己。
2. `_measureCells`（`table_block.dart`）去掉 `maxLines: 1` 与 `ellipsis`，改为 `layout(minWidth: 列宽, maxWidth: 列宽, textAlign: cell.align)`，多行也按列对齐；`_contentHeight` 取各格 painter 高度最大值，行高随内容增长。
3. `_chipsFor` 支持多行：单行时沿用原来的整行合并；多行时按 `LineMetrics` 逐视觉行合并 boxes，底片 y 用 `line.baseline - drop`。
4. `highlightRects` 单行格仍返回整行高度；多行按视觉行返回 `[textX + box.left, textX + box.right] × 行高`，避免相邻行高亮叠色。
5. painter 共享缓存的键加入 `TextAlign`（`(memo, 列宽 1/4px, align)`），对齐方式变化时不会复用旧 painter。
6. `offsetAt / caretRectAt / _textTop` 无需改动：`getPositionForOffset / getOffsetForCaret / getFullHeightForCaret` 原生支持多行。

验收结果（本机）：

| 项目 | 结果 |
| --- | --- |
| `flutter analyze lib test` | No issues found |
| `flutter test --exclude-tags perf` | 862 项通过 |
| `flutter test --tags perf` | 全过；100 × 10 同格打字 5.82 ms/次（P0 记录为 6.08~8.53）、冷开 523.97 ms、表外打字 ratio 1.07 |
| 窄表像素不变 | `table_wrap_test.dart` 锁定 80px 列宽 / 160px 表宽 / 28px 行高；右对齐格贴 `cell.right - 8` |
| 宽表换行 | 4 列宽内容：每列 ≥ 88px + 内边距，表宽铺满可用宽，表头单行、数据行变高，无负字距 |
| 偏移往返 | 每格**内容**范围内全部偏移 `caretRectAt → offsetAt` 一致（内边距空格不计，其折行归属本就不唯一） |

行为变化（可接受，已同步测试）：展开某个格子的源码时，源码比渲染态多出标记字符（如两颗反引号），窄表里若该格正好是该列最宽的一格，就会多占一行高度。列宽与其它行高度不变；`live_editor_widget_test.dart` 的「展开一格」用例改为断言这一点，不再要求逐像素不变。

## 10. P2 零散缓存实施记录

`_CellMemoStore` 新增三份与实例同生共死的缓存（环境变化或宿主换实例时随 `clear()` 释放）：

1. `_probes`：行内代码探针的 `(基线到顶距离, 行高)`，键为 `(样式, 探针文字)`。原先每条 code run、每次测量都新建 `TextPainter` 并布局一次；探针通常只有一个字符，开销全在建对象上。
2. `_overhangs`：`_middleOverhang` 的结果，键为 `(样式, 盒子高度)`。原先每张表每次测量都新建一个 `TextPainter`。
3. `_grips`：抓手图标 painter，键为颜色（强调色 / 三级文字色两种）。原先每帧、每个可见抓手都新建并布局一次，绘制后立即释放。

存放位置选在 `_CellMemoStore` 是因为它就是 `LiveTableBlocks` 的「按实例缓存」所有者，行块已经持有它，不必再给行块加构造参数。

实测（本机，`flutter test --tags perf`，与 §9 同一台机器）：

| 场景 | P1 后 | P2 后 |
| --- | --- | --- |
| 冷开（1,867 行，20 张表） | 523.97 ms | 468.17 ms（−10.7%） |
| 100 × 10 表冷布局 | 92.85 ms/build | 89.05 ms/build（−4.1%） |
| 100 × 10 表内同格打字 | 5.82 ms/次 | 5.98 ms/次（噪声范围内） |
| 表外打字 ratio | 1.07 | 1.02 |

`flutter analyze lib test` 无问题；`flutter test --exclude-tags perf` 862 项、`flutter test --tags perf` 全部通过。

## 11. P2 表头开关实施记录

- `TableCommands.setHeader(block, {header, row, column})`（`table_model.dart`）：表头 = 第一行 + 其后的分隔行，两者一起加、一起删；行本身不动，所以关掉再打开不会丢数据。目标状态与现状相同时直接返回原文，不重新 `render`（否则会把用户 `|` 周围的空格规范化掉），光标仍落回原格。
- `setTableHeader(value, {header})`（`markdown_actions.dart`）：解析光标所在表、取当前格，切换表头。
- 菜单放在「表格工具 ▸ 行」末尾，分隔线之后；有表头显示「取消表头」，否则「设为表头」，图标 `LucideIcons.tableProperties`。
- 测试：
  - `table_model_test.dart`：无分隔表 → 设为表头后第一行为表头、补出等宽分隔行、光标仍在原格；取消后分隔行与对齐一并消失、行数不变；已是该状态时原文逐字不变。
  - `editor_context_menu_test.dart`：在「行」子菜单里两次切换，文案随 `hasHeader` 变化，表格源码在 `| a | b |\n| c | d |` 与带分隔行之间往返。
- 验证：`flutter analyze lib test` 无问题；`flutter test --exclude-tags perf` 865 项、`flutter test --tags perf` 全部通过。
