03主区的四个视图

MainView { note, graph, canvas, image } 是 AppShell 的局部 state，不落盘（白板例外）。 四个视图叠在同一个 Stack 里，用 Offstage 藏起来而不是从树上摘掉——为了保住撤销栈、视口和滚动位置。 图谱和白板是懒建的：第一次点开才进树，之后一直挂着。

视图进树条件谁管「开没开」标签页右栏持久化
正文 note 永远在 MainView.note 每篇开着的笔记一枚，可多个 显示 标签会话
关系图谱 graph _graphOpened _graphOpened + _mainView 一枚，点 × 才关 整栏收起 不持久化
白板 canvas _canvasOpened CanvasController.path + _mainView 固定 key canvas-tab，只有一枚 显示 路径 + 是否激活
图片 image _imagePath != null _imagePath + _mainView 固定 key image-tab，只有一枚 整栏收起 不持久化
结构上的不一致：「当前在看哪个视图」是一个枚举 _mainView，但「这个视图开没开」散在三处—— _graphOpened 布尔、_imagePath 可空字符串、CanvasController.path 可空字符串。 于是每个入口（功能栏、标签、文件树、双击卡片）都得同时改两三个变量，漏一个就是「标签还在但点不动」或者「切过去一片空白」。

04各区域内部分层

每一块都是「一列：固定高的头 + 可伸缩的身子 + 固定高的脚」，只有主区是 Stack。

标题栏 40px · chrome 色 · 底边 1px

08重构时最紧的几处耦合

不是意见，是从代码里读出来的事实。这些地方一动就会牵连三四个文件。

01

标题栏被动接收两个「接缝」数字

AppShell 的 LayoutBuilder 算出 leftInset（rail + 左栏 + 拖拽条）和 rightInset（右栏宽或 0）， 传给 AppTitleBar，标题栏再用它们把标签条和三开关摆到像素位置上。也就是说标题栏知道下面每一栏多宽。 想改成分栏（比如加一条底部状态栏、或把右栏改成抽屉），这两个数字的算法得跟着一起改，而且它还在专注模式、侧栏收起、窗口变窄三种情况下有分支。

02

「视图」和「开没开」是两套状态

_mainView 说现在看哪个，_graphOpened / _canvasOpened / _imagePath 说哪个还活着。 两者组合出四种非法状态（比如 _mainView == image 但 _imagePath == null）， 所以 _selectMainView 里塞了一串前置判断和兜底（白板没文档就先新建、图片没路径就什么都不做）。 改成「一个视图列表 + 当前下标」这类模型，这四个字段能收成一个。

03

右栏三租户的互斥写在设置层

三个 *Visible 布尔由 SettingsController 的 setter 互相置假来保证，壳子里再各写一遍 if (showXxx)， 标题栏又各写一遍 selected:。加第四个租户要改五处（三个 setter、两个 if、一个 toggle）。 换成 rightPanel: RightPanel? 一个可空枚举，五处变两处。

04

主区四层全挂在同一个 Stack，靠 Offstage 保状态

这是刻意的（撤销栈、视口、滚动位置都在 State 里），代价是四个视图永远同时活着： 白板挂着就会监听键盘、图谱挂着就可能被 notes 通知触发重算。切视图时还要手动把焦点收回外壳， 白板更要等一帧再 requestFocus。改布局时要保证这四层的父级仍然是同一个 StackFit.expand，否则尺寸会变。

05

三个入口都能切视图，逻辑分散

功能栏（onOpenGraph / onOpenCanvas）、标题栏标签、文件树（onOpenCanvas / onOpenFile）各调各的， 最后都汇到 _selectMainView。但它前面的「白板没文档就新建」「图片没路径就忽略」是散在调用方的约定， 不是一处守卫。加第五个视图时，这三个入口都得记得改。

06

白板的会话恢复分两段

main.dart 在 vault 读完之后按 sessionCanvasPath 重开文档，AppShell 只负责「文档来了就切过去」（_pendingCanvasActivate）。 两段之间靠 CanvasController 的通知接力。任何把启动流程或壳子初始化顺序改动的重构都会打断这条链。

07

通知浮层会压在右栏上

NoticeHost 是 Stack 里最后一个 Positioned，left: 10, right: 10，对齐右上角。 右栏有内容时它盖住大纲/表格顶部。这是已知的、被接受的取舍（代码注释里写了「唯一允许浮起来的 chrome」）， 但如果重构后右栏变成常驻工具栏，这条得重新决定。

08

两套宽度、两套行高、两套网格

左栏 listWidth 与右栏 rightPanelWidth 各自独立但共用一套 ResizeHandle； 行高 28、面板头 32、工具条 40、脚 28 全在 AppLayout 里，但白板有一套自己的 canvas* 令牌。 重构时把「壳子尺寸」和「纸面尺寸」分开命名，比现在混在一个文件里好找。

一句话总结现状：壳子是一个 Column[标题栏, 四区 Row]，四区里只有主区是容器（四视图 Stack）， 其余三块都是「一个面板 + 一个拖拽条」。复杂度不在层级深度上——深度只有五六层——而在 标题栏要反算下面各栏的宽度、视图状态分散在四个对象里、右栏三个租户靠三个布尔互斥这三件事上。
